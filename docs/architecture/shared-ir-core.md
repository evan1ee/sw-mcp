# 3.4 Shared IR Core

> Specification v1.30, section 3.4. Index and section map: [specifications/README.md](../specifications/README.md).

The shared IR core is what every IR module, derived artifact and tool contract has in common: identifiers, references, units, numbers, revisions and the IR bundle (3.3). It is normative. Schemas in `schemas/common/` implement it (ADR-035), and every example in this specification follows it.

## 3.4.1 Identifiers

| Kind | Grammar | Scope | Example |
| --- | --- | --- | --- |
| Module key | one of `part`, `assembly`, `design_intent`, `drawing_intent`, `drawing_layout`, `drawing_template` | Global | `drawing_intent` |
| Document ID | `[A-Za-z0-9][A-Za-z0-9._-]{0,127}` | Unique per module key within a project store | `BRK-001-DI` |
| Item ID | `[a-z][a-z0-9_]{0,63}` | Unique within one module document | `bore_1`, `bore_dia` |
| Datum label | `[A-Z]{1,2}`, excluding `I`, `O`, `Q` (ISO 5459) | Unique within one Drawing Intent | `A` |
| Revision | Integer ≥ 1 | Per module document | `3` |

- IDs are case-sensitive and never reused within their scope, even after deletion.
- Item IDs are chosen by the author of a built module (agent or engineer). In read-only Part Feature Graphs they are generated by the Read path (5.8).
- Display names (`Boss-Extrude1`, `前视基准面`) are never IDs (5.3.6). They appear only in `display_name` fields and reports.
- **Collections of identified items are JSON objects keyed by item ID** (ADR-048), never arrays of objects with an `id` field: `"nodes": { "bore_1": { … } }`. The key is the item's ID; the item carries no `id` of its own. Where order matters, the item has an explicit integer field (`sequence`, `tree_order`). Arrays hold only ordered values and sets of references.

## 3.4.2 References

A reference is a string. Its kind is fixed by the schema type of the field that holds it, never guessed from its shape. Parsers reject a reference whose form does not match its field's type.

| Type | Form | Resolves to | Example |
| --- | --- | --- | --- |
| `DocumentRef` | `<module>:<document_id>` or `<module>:<document_id>@<revision>` | A module document, optionally at a pinned revision | `part:bracket@4` |
| `ItemRef` | `<module>:<document_id>[@<revision>]/<item_id>` | An item in another module document | `design_intent:BRK-001-DES@2/r1` |
| `LocalRef` | `<item_id>` | An item in the same module document | `bore_dia` |
| `IntentItemRef` | `<kind>:<id>`, kind is `scheme`, `critical`, `gdt`, `datum`, `finish` | An item of the drawing's Drawing Intent or its Resolved Scheme (11.10.1) | `scheme:ds_bore_1_diameter_b41219`, `datum:A` |
| `ParamRef` | `<feature_id>.<parameter>` | A parameter of a node in the Part Feature Graph the module documents | `bore_1.diameter`, `sketch_bore.x` |
| `GeometryRef` | `<feature_id>.<role>` (feature plus role, 11.1) | An entity defined by a feature-type role | `bore_1.cylindrical_face` |
| | `geo:<reference_id>` | A stored geometry reference (section 7, `inspect_geometry`); `<reference_id>` follows the item-ID grammar **[Builder's call]** | `geo:g7f3a21c0` |
| | `plane:front` \| `plane:top` \| `plane:right` \| `origin` | Standard planes and the origin, by role (5.3.6) | `plane:right` |
| | `datum:<label>` | The datum feature's geometry, per its `applies_to` | `datum:A` |
| `SolidWorksDimRef` | `swdim:<full name>` (stopgap, 11.1) | A SOLIDWORKS dimension by full name; converted to a `ParamRef` at intake and kept only for reporting | `swdim:D1@Sketch1` |

Rules:

1. **Scoped references.** Some fields refer into exactly one other document, fixed by the module itself, so they never carry a document ID:

   | Field | Resolves in |
   | --- | --- |
   | `ParamRef`, feature-plus-role `GeometryRef` in a Drawing Intent | The Part Feature Graph named by its `documents` field |
   | `GeometryRef` in an Assembly Graph mate | The part graph of the mate target's `component` |
   | `requirement` in a Drawing Intent | The Design Intent named by its `design_intent` field |
   | `realizes` in a Part Feature Graph, `targets` in a Design Intent | Functional feature names of the Design Intent in the same bundle (ADR-024) |

   A scoped reference whose document is absent (no `design_intent`, no Design Intent in the bundle) is a validation error, except `realizes`, which is ignored when no Design Intent is present (3.3 rule 4).
2. **Parameters and roles never share names.** Each feature type's schema defines its parameter names and role names as disjoint sets, so `bore_1.diameter` and `bore_1.axis` cannot be confused even outside a typed field.
3. **Cross-module references are `DocumentRef`, `ItemRef` or a scoped reference from rule 1** (3.3 rule 3). A module never refers to another module's internals by any other form. Exception: `drawing_template` field `source` candidates are late-bound lookup paths, not bundle references (11.12).
4. **Pinned or floating.** A `DocumentRef` or `ItemRef` without `@<revision>` floats to the latest revision when the bundle is validated. Validation records the revision it resolved to, and every stored artifact (plans, Resolved Schemes, reports) records only pinned references.
5. **Lists are always arrays.** A field that may hold more than one reference is an array, even when it holds one (`targets`, `covers`, `datums`). A field that holds exactly one reference is a single string.
6. **Unresolvable means error.** A reference that cannot be resolved to exactly one target is a validation error (`IR_REFERENCE_UNRESOLVED`, or `REF_AMBIGUOUS` for geometry, ADR-037). It is never dropped or guessed (7.4).

## 3.4.3 Units and numbers

- **Lengths.** Each module document declares `units`: `mm` or `in`. Every length in that document uses it. Drawing sheet coordinates are always millimetres (11.11).
- **Angles** are always degrees in every IR, derived artifact and tool response. The adapter alone converts to radians (8.3 rule 9).
- **Other quantities** use SI with an explicit unit in the field name or schema (`mass_kg`, `ra_um`). Counts are integers.
- **Numbers** are finite JSON numbers. `NaN`, infinities and numeric strings are rejected.
- **Comparison.** Two values are equal when they differ by no more than the quantum of their quantity kind:

  | Kind | Quantum |
  | --- | --- |
  | Length | 1e-6 mm (1e-7 in when the document is in inches) |
  | Angle | 1e-6° |
  | Ratio, factor | 1e-9 |
  | Count | exact |

  Geometric and verification tolerances (10.3, 7.4) are separate and configurable; the quantum only decides whether two stored numbers are the same value.
- **Equality and hashing differ.** Comparison uses the quantum as a tolerance, while hashing (3.4.4) uses each number rounded to its quantum. Two values can therefore compare equal and still hash differently (`1.0000004` and `1.0000006` mm round to `1.0` and `1.000001`), and tolerance equality is not transitive. Equivalence of stored documents (6.4) is decided by hash, never by comparing numbers one by one.
- **Text** is UTF-8, normalized to Unicode NFC on input.

## 3.4.4 Canonical form and hashes

Anything that is hashed, compared for "equivalence" (6.4) or used to derive an ID is first put in canonical form:

1. Validate against its schema and fill no defaults. Omitted optional fields stay omitted, so a document and its explicit-default twin hash differently, and the compiler records filled defaults only in the plan (12.3 rule 5).
2. Round every number to the quantum of its kind (3.4.3).
3. Sort arrays whose schema marks them unordered (`covers`, `targets`, sets of IDs). Ordered arrays (sketch geometry, plan operations) keep their order.
4. Serialize with RFC 8785 (JSON Canonicalization Scheme).

A content hash is `sha256:` followed by the lowercase hex SHA-256 of that serialization.

**Derived IDs.** A Resolved Scheme entry ID (11.10.1) is `ds_<slug>_<hash6>`. `<slug>` is the first entry of `covers`, or else the `to` target of `measures`, with every character outside `[a-z0-9_]` replaced by `_` and the result cut to 40 characters. `<hash6>` is the first six hex characters of the content hash of `{kind, covers, measures, source}`. On the rare collision of two different entries, `<hash6>` grows to eight, then twelve characters. The ID depends only on what the entry dimensions, never on insertion order.

## 3.4.5 Documents, revisions and bundles

**Document header.** Every module document starts with:

| Field | Description |
| --- | --- |
| `module` | Module key (3.4.1) |
| `id` | Document ID. Supplied by the author, or assigned by the store as `<module>-<ULID>` when absent |
| `schema_version` | `<major>.<minor>` of the module's schema (ADR-035, ADR-042) |
| `units` | `mm` or `in` (Drawing Layout IR: always `mm`) |
| `revision` | Set by the store. Ignored on input; a mismatch with `expected_revision` is checked separately (13.1) |
| `origin` | Part Feature Graph only: `built` or `read` (5.1) |

**Revisions.**
- The store assigns revision 1 when a document is created and adds 1 for every accepted change. Rejected changes create no revision.
- A stored revision is immutable. It records its content hash, parent revision, timestamp and the `request_id` that created it.
- **`apply_part_graph` (part chain MVP) [Builder's call].** A graph with a new ID needs no `expected_revision` and gets revision 1. An existing ID with identical content (the canonical form, 3.4.4, ignoring `revision`) reuses its revision and creates none. An existing ID with different content needs a matching `expected_revision`; without one the call fails with `REV_CONFLICT`, so one agent cannot silently replace another's graph. A matching `expected_revision` makes the new content revision n + 1. This is the one exception to the rule that `expected_revision` is required on every mutating tool that changes a store document (12.4.2).
- A read-only Part Feature Graph (`origin: read`) is linked to the part's identity (13.1). It gets a new revision only when the part's fingerprint changes. It cannot be changed through `update_part_graph`.
- Derived artifacts (3.3 rule 8) have no revisions. They are keyed by the pinned revisions, fingerprints and pipeline version they were produced from, and a different key is a different artifact.

**IR bundle manifest.**

```json
{
  "bundle_schema_version": "1.0",
  "modules": [
    "part:bracket@4",
    "design_intent:BRK-001-DES@2",
    "drawing_intent:BRK-001-DI@3"
  ]
}
```

- `modules` is a list of `DocumentRef`. At most one document per module key, except `part`, which may list one document per component of an Assembly Graph in the bundle, and `drawing_template`, which may list multiple documents (one per sheet format used across sheets).
- Floating references are pinned at validation (3.4.2 rule 4). The validated bundle, with every reference pinned, is what plans and reports record.
- Validation order (3.3 rule 1): each module against its schema; each module's own semantic rules; declared dependencies present (3.3 rule 2); cross-module references resolved; ownership and fallback rules (3.3 rule 4). Errors from independent modules are all reported.
- A bundle lists only stored documents. Documents reach the store by value through `create_*` and `apply_*`, and change through JSON Patch `update_*` calls (ADR-048).

## 3.4.7 Validation errors

Agents correct IR from validation errors, so their form decides how many attempts a fix takes.

- **Every error** carries `code` (ADR-037), `pointer` (RFC 6901 JSON Pointer into the submitted document; with ID-keyed collections it names the item, for example `/nodes/bore_1/parameters/diameter`), `message` (one line), and where useful `expected` (the allowed values or type) and `ref` (the reference that failed to resolve).
- **Stages.** Schema validation runs first and stops the pipeline if it finds errors: semantic rules on a malformed document produce noise. Semantic validation of independent modules then runs for all of them. Cross-module checks run only when every module passed its own checks (3.4.5 validation order).
- **All errors of a stage are reported**, not just the first, up to 50 per call with a count of the rest.
- **Order is deterministic:** by pointer, then by code. Pointers are compared token by token: two tokens that are both array indices compare as numbers, and any other pair compares by Unicode code point, so `/modules/2` comes before `/modules/10` **[Builder's call]**. The same document always gives the same error list.
- **Warnings** use the same form with `severity: "warning"`. They never stop a stage and never block storing a document. Example: a `realizes` name ignored because no Design Intent is present (3.4.2 rule 1).
- **Patches** (ADR-048) are validated as the whole document they produce. Pointers refer to that resulting document, and the error also names the failing patch operation's index.

## 3.4.8 Schema files [Builder's call]

Approved by the owner on 2026-11-04. How the files in `schemas/` (ADR-035) are named and how they carry what the canonical form (3.4.4) needs.

- **Identity.** Every schema's `$id` is `https://sw-mcp.invalid/schemas/<directory>/<file>`. The `.invalid` top-level domain (RFC 2606) never resolves: an `$id` is a name, not a location. Schemas refer to each other by relative `$ref`, for example `../common/v0.json#/$defs/DocumentRef`.
- **Files.** Shared-core types are `$defs` in `schemas/common/v0.json`. The error catalogue (ADR-037) is `schemas/common/errors.json`. The bundle manifest is `schemas/bundle/v1.json`, matching `bundle_schema_version` `1.0` (3.4.5).
- **Major version 0 is unstable.** A contract is published at major 0 during Phase 0 and Phase 1 development. Any change is allowed at major 0, and the compatibility diff (ADR-042) skips it. The rules of ADR-042 apply from a contract's first release at major 1.
- **Number kinds.** A numeric schema carries the annotation `"x-quantity"`: `length`, `angle`, `ratio` or `count`. The `$defs` `Length`, `Angle`, `Ratio` and `Count` in `common/v0.json` carry it, and module schemas use them by `$ref`. Canonicalization quantizes each number to the quantum of its kind (3.4.3); a number without a kind is left as written.
- **Unordered arrays.** An array that is a set (3.4.4 step 3: `covers`, `targets`, sets of IDs) carries `"x-unordered": true`. Canonicalization sorts its elements by their canonical serialization.
- **Error catalogue.** `errors.json` lists each code as a `oneOf` branch with `const`, a one-line `description` and `"x-retryable"`: the default `retryable` value (ADR-037) for that code. A response may override it for one error. The values mean:
  - `safe`: nothing changed, and the same call may be repeated unchanged (for example `BACKEND_BUSY`, `STORE_LOCKED`);
  - `after_fix`: the caller must change its input or first inspect the state the call may have left. Timeouts, interruptions and a lost add-in connection are `after_fix`, never `safe`, because the operation may have run (8.3 rule 8, 13.2.3);
  - `never`: the same call cannot succeed in this environment (permissions, unsupported versions or features, cancelled or unknown jobs).
- **Integers.** `"type": "integer"` accepts only JSON numbers written without a fraction or exponent (`2`, not `2.0`), and every integer schema sets `"maximum": 9007199254740991` (2^53 − 1) so that RFC 8785 can serialize it.
- **Pattern-keyed objects.** Schemas restrict the keys of ID-keyed collections with `propertyNames`, never `patternProperties`.
- **Patterns** are anchored (`^…$`) and use only syntax that ECMA-262, Python `re` and .NET agree on. Implementations match a whole string, so a trailing newline never passes.
